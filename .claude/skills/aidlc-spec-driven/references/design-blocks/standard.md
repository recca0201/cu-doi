# Standard Design Document Guidance

Use this guidance for Phase 2 `design.md` documents. It defines the document
shape only; write project-specific content from the approved requirements,
codebase analysis, UI handoff context, and research.

## Template Structure

```markdown
# Design: {Feature Name}

## Overview

| Review item | Summary |
| --- | --- |
| **Goal and approach** | [What is being built and the chosen approach] |
| **In scope** | [Included behavior and boundaries] |
| **Out of scope** | [Explicit exclusions] |

## Open Questions
[Unresolved API, copy, design-system, data-contract, or implementation
questions, including UI ambiguity carried forward from `mockup.html`. Write
`None` when there are genuinely none — a hidden assumption is not `None`.]

| # | Question | Blocking? | Working assumption |
| --- | --- | --- | --- |

## Architecture
[High-level structure, patterns]
[Prefer Mermaid diagrams to visualize the architecture, placing the feature inside the existing system with new vs existing nodes marked. Include more than one diagram when useful. For integration or service/system flow, prefer a Mermaid sequence diagram.]

[Follow with 2–4 concise bullets covering the existing pattern, proposed delta, affected boundaries, and the key security, performance, reliability, or observability constraint when applicable.]

## Components and Interfaces
[Start with a tree view of new and changed files in architectural reading order. Mark each file `[NEW]` or `[CHANGED]`; the tree is a review map, not implementation sequencing.]

[Ground the tree entries in real code. For `[NEW]` files, cite the verified precedent path or state `No precedent`. For `[CHANGED]` files, cite any precedent used for the new behavior. Use real code paths, not assumptions.]

[Describe the design-critical interfaces, components, APIs, and functions with signatures, not implementations, each followed by 1–2 concise sentences of behavior. Do not include function bodies, implementation steps, or lengthy comments; code fences are reserved for contracts only. When a contract changes, mark only the new or changed elements so the delta is visible.]

## UI Design Specification *(optional - include only when mockup.html exists or was generated)*

> UI handoff: [mockup.html](./mockup.html)
> UI source of truth: detailed visual structure, interaction states, accessibility markup, and full token/mapping metadata remain in `mockup.html`.

### Implementation-Critical UI Constraints
[Only the design constraints that materially affect architecture, interfaces, or task planning. Preserve original token identifiers only where implementation needs them directly.]

### Screen / Component Summary
[High-level surfaces or component groups, key states, non-obvious interaction patterns. Do not repeat the visible HTML structure from `mockup.html`.]

### Design System Dependencies *(optional - include only when a shared design system is in scope)*
[Implementation-critical component families, wrappers, tokens, or icons carried forward from `mockup.html`]

### Responsive Notes
[Breakpoint changes that affect layout or component behavior]

## Data Models
[Schemas, entities, relationships. For changes to existing models, mark which tables/fields are new vs changed rather than restating the full unchanged schema. Use a table format to display when possible.]

## Error Handling
[A table, one row per failure mode or edge state:

| Scenario | Handling |
| --- | --- |
]

## Testing Strategy
[Use only the applicable test levels. Keep this as a strategy summary; do not include detailed test cases or test code.

| Test level | What to verify |
| --- | --- |
| Unit | [Core logic and component behavior] |
| Integration | [Interfaces, data flow, and service interactions] |
| E2E | [Critical user or system flow] |
]

## Design Decisions
[A table, one row per decision:

| Decision | Choice | Alternative rejected | Why (one line) |
| --- | --- | --- | --- |
]
```

## Rules

- **Readable and lean (whole document)**: use clear headings, short sentences and paragraphs, and bullets or tables where they are easier to scan than prose. State each fact once. Keep only approval-relevant decisions and contract-level detail; omit implementation code and long explanations.
- Keep the standard section headings unless the feature genuinely makes a section irrelevant; use `N/A` briefly instead of deleting required traceability.
- Reuse the optional `## UI Design Specification` section only when `mockup.html` exists or is generated by the UI handoff workflow.
- Keep UI handoff details lean: reference `mockup.html` for complete visual structure, states, accessibility markup, and token inventories.
- Include implementation-facing decisions, interfaces, and failure modes; avoid implementation tasks, approval text, and next-step boilerplate.
- Make the delta visible: when a section modifies an existing interface, API, schema, or data model, mark which elements and fields are new vs changed (e.g. a `// new` / `// changed` / `// added` marker) instead of restating the full unchanged shape — the reader should see what changed without diffing against the current code.
- Carry unresolved API, data, copy, Figma, and design-system uncertainty into `## Open Questions`.
